# vgpu demos

> **Note:** All code in this repository was generated by AI ([Claude Code](https://claude.com/claude-code)).

Interactive WebGPU demos built with [vgpu](https://vgpu.sh/docs) — a typed, agent-first WebGPU library — and plain TypeScript + Vite. Each example lives in its own folder and is picked from the sidebar; every example has a controls panel so it can be driven live during a presentation. A **Performance tests** tab measures what the effects cost when a page has many of them.

## Performance tests

The **Performance tests** tab (bottom of the menu, `#performance`) puts N copies of an effect — smoke, liquid button or photo reveal — on a simulated page and measures them live.

### Three strategies

The same effects can be wired into a page in three ways. Pick one with the cards at the top of the tab.

| | Naive (as in demos) | Shared device | Production |
|---|---|---|---|
| In one sentence | Every effect brings its own engine. | One engine powers all effects. | One engine, and only what you can see moves. |
| GPU devices (`init()`) | one per effect | one | one |
| Shaders compiled / images uploaded | once per effect | once | once |
| Animation loops | one per effect | one | one |
| Draws effects scrolled out of view | yes | yes | no |
| Draws effects standing still | every frame | every frame | once, then stops |
| When the vgpu code loads | with the page | with the page | after the page has loaded and gone idle |

In all three, tiles with a photo show it as a plain `<img>` until their first frame; in Production that image is also what Lighthouse scores as LCP and what visitors without WebGPU keep seeing. Naive is how the demo pages are written, Shared device shows what sharing one device saves on its own, and Production is the setup to ship.

### Controls

- **Effect** and **Instances on the page** (1–64).
- **Tile size** — 0 % puts all N tiles on screen at once; 100 % makes one tile fill the screen and the rest scroll.
- **Animating at once** — the share of tiles playing their show/hide cycle (default 25 %).
- **Sync animations** — plays all animating tiles in step instead of staggered: the worst case, where every effect peaks in the same frame. Click again to stagger them.
- **Max device pixel ratio** — 1×, 1.5× or 2×.
- **Emulate slower hardware** — browsers can't throttle the GPU, so the tab approximates a slower device: every tile is drawn N times per frame (same image, N× the GPU work) and the effect's JS is stretched N× with a busy-wait. Presets (laptop ~2020, older laptop ~2018 with Intel UHD 620, budget phone) turn rough "N× slower at 60 Hz" ratios into per-frame multipliers for the current display. The ratios assume an Apple M5 Pro-class machine and are estimates; for whole-page CPU throttling use Chrome DevTools → Performance → CPU.

### Metrics and thresholds

Every value is marked ✓ good, ! needs work or ✕ poor. Frame thresholds scale with the display's frame budget (8.3 ms at 120 Hz, 16.7 ms at 60 Hz); page-load thresholds are Google's.

| Metric | ✓ Good | ✕ Poor |
|---|---|---|
| FPS | ≥ 95 % of the refresh rate | < 80 % |
| Frame time p95 | ≤ 1.25 × budget | > 2 × budget |
| Dropped frames (> 1.5 × budget) | ≤ 5 % | > 15 % |
| Main-thread JS per frame | ≤ 2 ms | > 4 ms |
| GPU time per frame | ≤ 50 % of budget | > 80 % of budget |
| First frame after mount | ≤ 100 ms | > 300 ms |
| Startup blocking (long tasks) | ≤ 50 ms | > 200 ms |
| Lighthouse score / LCP / TBT / CLS | ≥ 90 / ≤ 2.5 s / ≤ 200 ms / ≤ 0.1 | < 50 / > 4 s / > 600 ms / > 0.25 |

GPU time is measured with `timestamp-query` as the span of a whole frame on the GPU (Chrome rounds it to 0.1 ms). It is not reported for Naive, because frames of separate devices overlap on the GPU and their times can't be added up.

### Benchmark and report

A status line above the tiles shows FPS, p95 frame time, JS and GPU time with their ratings, so the effect of every setting is visible without scrolling the panel.

**Run benchmark** mounts every strategy at 1, 4, 8, 16 and 32 instances (optionally 64) with the current settings, warms up for 1 s and measures for 3 s each. Controls are locked while it runs; the same button stops it after the current step. The result is charts, a table with a verdict per row, and three downloads: an HTML report (findings, strategies, charts, thresholds, method; prints to PDF), Markdown and JSON.

### Lighthouse

Page-load cost is measured against a production build:

```bash
npm run perf:lighthouse                                   # smoke, 12 cards, mobile + desktop, 1 run each
npm run perf:lighthouse -- --fx=smoke,reveal --count=6,24 --runs=3 --no-build
```

The script builds the app, serves `bench.html` (a landing-like page with N effect cards, `?fx=&count=&strategy=none|naive|shared|production`), runs Lighthouse with the mobile and desktop presets, and measures runtime FPS in the same Chrome. `strategy=none` is the same page with static images and no WebGPU — the baseline. It writes `perf-reports/summary.md`, `summary.json` (shown in the tab) and the full Lighthouse reports; `perf-reports/` is git-ignored.

### Results so far

Measured on 2026-10-15 on a MacBook with Apple M5 Pro, Chrome 155, 120 Hz display, DPR 2, 25 % of tiles animating. Treat them as a best case and repeat on the slowest device you target.

Smoke (the heaviest effect), in-tab benchmark:

| Instances | Naive | Shared device | Production |
|---|---|---|---|
| 8 | 120 fps | 120 fps, GPU 4.6 ms | 120 fps, GPU 3.3 ms |
| 32 | 120 fps | 120 fps, GPU 5.6 ms | 120 fps, GPU 3.5 ms |
| 64 | 112 fps, 64 GPU devices | ✕ 99 fps, 21 % frames dropped | ✓ 120 fps, GPU 3.6 ms |

The liquid button and the photo reveal are light: under 1 ms of GPU per frame in Production even at 32 instances. Main-thread JS stayed under 2 ms per frame and startup caused no long tasks in every run.

Lighthouse, 12 smoke cards (median of 3 runs):

| Strategy | Mobile LCP | Desktop LCP | TBT | CLS | Score |
|---|---|---|---|---|---|
| none (static images) | 0.90 s | 0.24 s | 0 ms | 0 | 100 |
| Naive | 1.67 s | 0.38 s | 0 ms | 0 | 100 |
| Shared device | 1.67 s | 0.39 s | 0 ms | 0 | 100 |
| Production | 0.91 s | 0.24 s | 0 ms | 0 | 100 |

Loading vgpu (~67 KB gzip with the shaders) together with the page delays the poster images on mobile by ~0.75 s; deferring it, as Production does, keeps LCP at the baseline.

### Recommendations for production

- Create **one** GPU device per page and share it between all effects.
- Draw only what is visible and moving; let idle canvases keep their last frame.
- Ship a poster `<img>` in the HTML and load vgpu with a dynamic `import()` after the page has loaded.
- Cap the device pixel ratio at 2 (or lower for large canvases).
- Check the GPU time per frame on a slower device or with the hardware emulation before adding more effects.

### Adding an example

1. Create `src/examples/<name>/index.ts` exporting `mount(root: HTMLElement)`, which renders into `root` and returns a cleanup function (stop the frame loop, `gpu.dispose()`).
2. Register it in `src/examples/index.ts` with an `id` (used as the URL hash) and a `title`. Entries with `tool: true` are listed at the bottom of the menu.

Shaders are plain `.wgsl` files imported directly (`import shader from './x.wgsl'`); the Vite plugin turns them into prepared vgpu shader sources. Validate one without a browser:

```bash
npx vgpu check src/examples/smoke-hover/smoke.wgsl
```

